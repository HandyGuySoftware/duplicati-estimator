Duplicati Size Estimator

Recommends --block-size and --dblock-size from a source profile and your destination characteristics.

How it works

The estimator is a two-step pipeline. First you profile your source data with a small Python or PowerShell script; that produces a compact JSON file describing the size distribution. Then you load that profile into this page, pick your destination details, and it recommends the two Duplicati size parameters along with projected backend file and block counts.

Step 1 — Profile your source data

Profile the folder (or folders) you intend to back up with either tool below — both produce the identical profile.json. Use whichever matches your platform.

Get the profiler scripts from the project repository — direct downloads: duplicati_profiler.py (Python) or duplicati_profiler.ps1 (PowerShell). On a raw-file page, use your browser's Save As to download it.

Python macOS, Linux, Windows — Python 3.7+

Standard-library only, so it runs anywhere — including directly on the NAS or server where the files live, over SSH. Write the profile to a file with -o: 

python3 duplicati_profiler.py /path/to/source -o profile.json

# Several locations at once — directories and/or individual files.
# They need not share a tree; overlapping paths are counted once.
python3 duplicati_profiler.py /data/photos /data/docs /mnt/archive.iso -o profile.json

PowerShell Windows and cross-platform — PowerShell 7+

A port that needs no Python — handy on Windows. Requires PowerShell 7+ (a free install from aka.ms/powershell, runs alongside the built-in Windows PowerShell 5.1): 

.\duplicati_profiler.ps1 C:\path\to\source -Output profile.json

# Several locations at once — pass them positionally (directories and/or files).
# Use positional args, not -Path a b c (that binds only the first value).
.\duplicati_profiler.ps1 C:\data\photos C:\data\docs D:\archive.iso -Output profile.json

Either profiler accepts one or more paths — directories are walked recursively and individual files are counted directly, all aggregated into a single profile.json. It records only aggregate statistics and a short list of the largest file sizes — never file names or paths — so the profile is safe to copy between machines. Symlinks are skipped by default (--follow-symlinks for Python, -FollowSymlinks for PowerShell).

Step 2 — Run the estimator

Load profile.json in Section 1 below (file picker or paste), set your destination and connection details in Section 2, and click Calculate. The recommendation and projections appear in Section 3; the reference rules behind them are in Section 4 · Guidelines. No data ever leaves your browser — all the math runs locally on this page.

Prefer the command line? A companion calculator (available for both Python and PowerShell) takes the same profile and prints the same recommendation. Get it and the usage docs from the project repository.

    4 · Guidelines

    These are the reference rules this calculator applies. They are first-pass heuristics grounded in Duplicati documentation and community forum guidance, not hard limits — treat the output as a sensible starting point to tune against your own data.

    Block size (--block-size) — immutable after the first backup

    • Base rule: about 1 KB of block size per 1 GB of source data (800 GB → 800 KB, 2 TB → 2 MB). This keeps the dedup-block count — and therefore the local database — manageable as the set grows.
    • Change pattern adjusts it: archival data (mostly added, rarely edited) tolerates larger blocks (×1.5); high-churn data (many small edits) favors smaller blocks (×0.6) so a small change re-uploads less.
    • Floor at 100 KB (Duplicati's default), applied after the change-pattern adjustment. Below this, the block database bloats with little benefit.
    • Scaling target: keep the tracked block count roughly under a few million. Real multi-TB users run 5–50 MB blocks for exactly this reason — the base rule lands there naturally (a 50 TB set → ~50 MB blocks).
    • Because it cannot be changed after the first backup, the recommendation errs toward future-proofing.

    Volume size (--dblock-size) — changeable anytime

    • Local / LAN: target about 10,000 backend files (index + block pairs) — total / 10000 × 2 — clamped to the 50 MB–2 GB range.
    • Remote / cloud: start around 200 MB (the range cloud users converge on), then adjust: slow upload (< 10 Mbps) → 100 MB so a failed transfer re-sends less; fast upload (≥ 200 Mbps) → ~500 MB for fewer files.
    • Daily download cap: a verify or restore pulls a whole volume, so the volume is held to about ¼ of any cap you set.
    • Unstable connection: capped at 100 MB to limit what has to be re-transmitted after a failed upload.

    Compression

    • Duplicati uses Zip/Deflate compression by default. Real-world savings depend almost entirely on data type.
    • Leave at 100% for already-compressed data (photos, video, music, zip/office files); lower it toward 70–90% for documents and code, or 40–60% for logs, text, and uncompressed databases.
    • The default (100%) never under-estimates storage or backend file counts, so it errs on the safe side.

    Guardrails the calculator flags

    • Error: block size larger than volume size (a dedup block must fit inside a volume), or block size below Duplicati's 10 KB hard minimum.
    • Note: block size above 1 MB or volume size above 1 GB — fine for large sets, but worth a deliberate look.
    • Warning: more than ~5,000,000 tracked blocks (database slows) or ~100,000 backend files (some destinations throttle large listings).
